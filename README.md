# 비밀번호 보안 도구 (`26-w12-password`)

## 소개

사용자가 비밀번호의 안전성을 스스로 진단하고, 암호학적으로 안전한 새 비밀번호를 발급받으며, 클라이언트 측 암호화 원리까지 직접 체험할 수 있는 **「클라이언트 중심 비밀번호 보안 점검 및 암호화 대시보드」**입니다. 

모든 연산(강도 분석, SHA-1 해싱, 난수 생성, AES-GCM 암·복호화)을 브라우저 내부(Web Crypto API)와 휘발성 메모리(`useState`)에서만 처리하며, 유출 조회 시에도 **k-익명성(k-Anonymity)** 모델을 적용해 비밀번호 원문이나 전체 해시가 외부 서버로 절대 전송되지 않도록 설계했습니다.

## Vite 프로젝트 직접 구성 경험

1. **빈 저장소에서 직접 프로젝트를 구성하며 느낀 차이점**
   - 지난주까지는 `package.json`, `vite.config.js`, 기본 디렉터리 구조가 이미 세팅된 저장소에서 기능 구현만 진행했지만, 이번에는 빈 저장소에서 `npm create vite@latest`로 직접 프로젝트를 초기화했습니다.
   - 의존성 패키지 설치(`npm install`), 개발 서버 구동(`npm run dev`), 빌드 구조와 진입점(`index.html` → `src/main.jsx` → `src/App.jsx`)의 연결 흐름을 처음부터 직접 세팅하면서 React + Vite 프로젝트의 전체 골격과 설정 파일의 역할을 명확히 이해할 수 있었습니다.

2. **`create-vite`의 파일 덮어쓰기 경험과 `.gitignore` 관리**
   - 프로젝트 초기화 과정에서 `create-vite`가 기존 저장소에 있던 `README.md`와 `.gitignore`를 기본 템플릿으로 덮어쓰는 것을 보며, 스캐폴딩 도구를 실행하기 전에는 기존 문서와 설정 파일을 반드시 백업하거나 `git diff`로 변경 사항을 확인해야 한다는 점을 체감했습니다.
   - `.gitignore`에는 기본 `node_modules`, `dist` 외에도 환경 변수 파일(`.env`, `.env.local`), OS 임시 파일(`.DS_Store`, `Thumbs.db`), 에디터 설정 폴더(`.vscode/`, `.antigravity/`)를 추가했습니다. 민감한 환경 변수나 개인 개발 환경 설정이 원격 저장소에 올라가 보안 사고나 협업 충돌을 일으키는 것을 방지하기 위해 필수적입니다.

## 나의 AI 기획·구현 과정

1. **AI 협업 방식**
   - **Gemini 웹(기획 및 프롬프트 설계) → Antigravity IDE(구현 및 보안 감사)**의 2단계 워크플로우로 진행했습니다.
   - 먼저 Gemini 웹에서 앱의 정체성, 강도 판정 기준, Web Crypto API 명세, 보안 제약 조건(`console.log` 및 `localStorage` 금지)을 구체화한 통합 프롬프트를 설계한 뒤, Antigravity IDE 에이전트에 전달해 UI와 핵심 로직을 구현하고 코드 전수 감사를 수행했습니다.

2. **비밀번호 "강도" 기준 설계**
   - 단순히 길이만 길다고 안전한 비밀번호가 아니므로 **3가지 복합 기준**으로 4단계(`매우 약함`, `약함`, `보통`, `강함`)를 판정하도록 설계했습니다.
     - **길이 점수**: 8자 미만(매우 약함), 8~11자(기본), 12~15자(우수), 16자 이상(최고점)
     - **문자 다양성**: 대문자(`A-Z`), 소문자(`a-z`), 숫자(`0-9`), 특수문자 포함 여부를 체크리스트로 평가
     - **취약 패턴 감점**: `1234`, `qwer`, `asdf`, `password`, `admin` 같은 흔한 패턴이나 동일 문자가 3회 이상 연속 반복(`aaa`, `111`)되는 경우 경고 메시지와 함께 강도를 `'약함'` 이하로 강제 하향

3. **구현 중 가장 막혔던 문제와 해결 과정**
   - **대소문자 불일치로 인한 유출 판정 오류**: Have I Been Pwned API 응답의 해시 접미사(뒤 35자리)는 모두 **대문자**로 내려오는 반면, JavaScript에서 `crypto.subtle.digest`의 `ArrayBuffer`를 16진수 문자열로 변환하면 기본적으로 **소문자**가 생성되어 유출된 비밀번호(`password`)도 "안전"으로 잘못 판정되는 문제가 있었습니다. 해시 변환 직후 `.toUpperCase()`로 대문자를 통일해 정확히 대조하도록 해결했습니다.
   - **UX 및 보안 트레이드오프 해결**: 유출 확인을 타이핑할 때마다 실시간으로 호출하면 중간 입력값의 해시 접두사까지 서버에 연달아 노출되고 불필요한 트래픽이 발생하므로, 강도 검사는 실시간(로컬 연산)으로 두고 유출 확인은 **「유출 여부 확인」 버튼을 눌렀을 때만 1회 요청**하도록 분리했습니다.
## 보안 점검 (사이버보안과 체크포인트)

1. **`Math.random()` 대신 `crypto.getRandomValues()`를 써야 하는 이유**
   - `Math.random()`은 내부 상태(시드) 기반의 일반 의사난수 생성기(PRNG)로, 출력값 일부를 수집하면 알고리즘을 역추적해 다음에 생성될 난수를 예측할 수 있어 보안에 취약합니다.
   - 반면 `crypto.getRandomValues()`는 운영체제가 수집하는 하드웨어 엔트로피를 기반으로 동작하는 **암호학적 안전 의사난수 생성기(CSPRNG)**이므로 공격자가 생성된 비밀번호를 예측하는 것이 수학적으로 불가능합니다.

2. **Network 탭 실제 요청 주소 검증**
   - 테스트 비밀번호 `password`(SHA-1: `5BAA61E4C9B93F3F0682250B6CF8331B7EE68FD8`) 입력 후 확인 시 F12 Network 탭에서 검증한 실제 요청 주소:
     - Request URL: `https://api.pwnedpasswords.com/range/5BAA6`
   - URL, Query String, Request Header, Payload 어디에도 **비밀번호 원문이나 40자리 전체 해시는 전송되지 않았으며**, 앞 5글자(`5BAA6`)만 전송되고 나머지 35글자의 대조는 브라우저 내부에서만 이루어짐을 확인했습니다.

3. **k-익명성(k-Anonymity) 방식의 한계점**
   - 비밀번호 원문과 전체 해시는 보호되지만, 서버 입장에서는 여전히 **조회한 해시의 앞 5글자(Prefix)**, 요청을 보낸 클라이언트의 **IP 주소**, 그리고 **요청 시각(Timestamp)**을 확인할 수 있습니다. 즉, "어떤 비밀번호를 찾았는지"는 숨길 수 있어도 "특정 IP 사용자가 특정 시점에 비밀번호 유출 조회를 요청했다는 사실"까지는 숨기지 못하는 한계가 있습니다.

## 나만의 확장 기능

- **`Add-Padding: true` 헤더 적용 및 가짜 응답 필터링**: 해시 접두사별 응답 본문의 패킷 크기(Byte) 차이로 비밀번호를 추측하는 트래픽 분석 공격을 막기 위해 요청 헤더에 `Add-Padding: true`를 포함했습니다. 또한 서버가 응답 크기를 맞추기 위해 섞어 보내는 유출 횟수 `0`인 가짜 해시 항목을 클라이언트 파싱 단계에서 걸러내도록 구현했습니다.
- **AES-GCM 암호화 금고 탭**: Web Crypto API의 `PBKDF2`(SHA-256, 100,000회 반복, 무작위 16바이트 Salt)로 마스터 비밀번호에서 키를 파생하고, `AES-GCM`(무작위 12바이트 IV)으로 비밀 메모를 암호화·복호화하는 기능을 추가했습니다. 마스터 키를 서버나 `localStorage`에 저장하지 않기 때문에 비밀번호를 분실하면 누구도 복구할 수 없는 영지식(Zero-Knowledge) 암호화 원리를 체험할 수 있습니다.
- **취약 패턴 감지 및 강도 강제 하향 로직**: 키보드 연속 배열(`qwer`, `asdf`), 연속 숫자(`1234`), 동일 문자 3회 이상 반복(`aaa`, `111`) 입력 시 즉시 보안 경고를 표시하고 강도 등급을 제한하는 방어 로직을 적용했습니다.
