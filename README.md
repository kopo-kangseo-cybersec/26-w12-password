# 비밀번호 보안 도구 (`26-w12-password`)

> 이 README는 실습을 완성한 뒤, 배포 직전 단계에서 직접 채워 넣습니다.
> 실습 안내와 완성 기준은 [`guide.md`](./guide.md)를 참고하세요.

## 소개

**CyberPass Guard**는 사용자의 비밀번호 보안성을 완벽하게 점검하고 안전하게 관리할 수 있도록 설계된 **사이버보안 점검 대시보드형 웹앱**입니다.

- **비밀번호 무저장 원칙 (Zero-Knowledge)**: 모든 강도 분석과 해시 계산은 브라우저 내부에서만 100% 로컬 연산되며, 입력된 비밀번호는 콘솔 출력이나 스토리지에 절대 저장되지 않습니다.
- **최소 전송 원칙 (k-Anonymity)**: 글로벌 유출 데이터베이스(Have I Been Pwned)와 대조할 때 비밀번호 원본이나 전체 해시를 보내지 않고, SHA-1 해시의 **앞 5글자(Prefix)만 전송**하여 프라이버시를 완벽히 보호합니다.
- **암호학적 안전성 (CSPRNG & Web Crypto)**: `Math.random()`을 철저히 배제하고 `crypto.getRandomValues()`를 사용한 비밀번호 생성기와 PBKDF2 + AES-GCM 기반의 클라이언트 암호화 메모 금고를 제공합니다.

## Vite 프로젝트 직접 구성 경험

1. **빈 저장소에서 `npm create vite@latest .`로 직접 프로젝트를 차려 보니, 지난주(미리 준비된 템플릿)와 비교해 무엇이 달랐나요?**
   - 이전 실습에서는 `package.json`, `vite.config.js` 등이 모두 사전 구성된 템플릿 환경에서 코딩에만 집중했으나, 이번에는 빈 폴더에서 프로젝트 초기화부터 직접 진행했습니다.
   - 프레임워크 선택 시 기본값(TypeScript) 대신 이번 과제 요구사항인 `React + JavaScript + Oxlint` 조합을 직접 방향키로 찾아 선택해야 했고, Netlify 및 GitHub Pages 배포 환경 모두에서 에셋 경로가 깨지지 않도록 `vite.config.js`에 `base: './'` 설정을 추가하고 `gh-pages` 의존성과 `deploy` 스크립트를 직접 구성해보며 프론트엔드 빌드 파이프라인의 전 과정을 깊이 있게 이해할 수 있었습니다.

2. **`create-vite`가 README.md와 .gitignore를 덮어쓴 것을 보고 무엇을 느꼈나요? .gitignore에 무엇을 추가했고, 왜 필요한가요?**
   - 도구의 초기화 템플릿이 기존 저장소의 중요 파일(기존 안내서나 템플릿 문서)을 경고 없이 덮어쓸 수 있음을 확인하고, 도구 사용 전 백업 및 Git 버전 관리의 중요성을 실감했습니다.
   - 특히 기본 생성된 `.gitignore`는 `.env.local` 등 파생 파일만 차단하고 **`.env` 파일 자체나 `.env.*`를 기본으로 차단하지 않는 보안 취약점**이 있었습니다.
   - 이에 따라 `.gitignore` 최하단에 아래 설정을 직접 보강했습니다:
     ```gitignore
     # 환경변수 — 절대 커밋하지 않습니다
     .env
     .env.*
     !.env.example
     ```
   - 비록 본 프로젝트는 클라이언트 순수 연산이라 별도의 API 키가 필요 없지만, *"프로젝트 셋업 즉시 민감 설정 파일 유출 경로 차단"*이라는 보안 개발자의 필수 원칙을 체득했습니다.

## 나의 AI 기획·구현 과정

1. **어떤 AI 협업 방식을 선택했나요?**
   - **Antigravity Implementation Plan 방식**을 선택하여 먼저 요구사항 명세서 기반의 아키텍처와 보안 체크리스트를 체계적으로 수립했습니다.
   - 이후 UI 컴포넌트(`StrengthAndBreach`, `PasswordGenerator`, `EncryptionVault`)와 순수 암호화 유틸리티(`crypto.js`, `strength.js`)로 모듈화하여 `oxlint` 린트와 `vite build`를 단계별로 검증하며 완성도를 높였습니다.

2. **비밀번호 "강도"의 기준을 어떻게 정했나요?**
   - 단순한 글자 수 확인을 넘어 실제 보안 취약 요소를 다각도로 평가하는 4단계 평가 모델을 설계했습니다:
     - **길이 점수**: 8자 미만(위험/감점), 8~11자(기본), 12~15자(가점), 16자 이상(최고 가점)
     - **문자 다양성**: 영문 대문자(`A-Z`), 소문자(`a-z`), 숫자(`0-9`), 특수문자(`!@#$%^&*` 등) 포함 여부를 개별 체크리스트로 검증하고 가점 부여
     - **알려진 취약 패턴 감점**: `1234`, `password`, `qwer`, `admin`, `abcd`, `asdf` 등 빈출 비밀번호 문자열 탐지 시 대폭 감점(-2점)
     - **반복 문자 감점**: `aaa`, `111` 등 동일 문자가 3회 이상 연속 반복되는 경우 감지하여 감점(-1점)
   - 이를 종합하여 5단계 게이지(매우 약함 / 약함 / 보통 / 안전 / 매우 안전) 및 직관적인 보완 권고 피드백을 실시간 제공하도록 구현했습니다.

3. **구현 중 가장 막혔던 문제는 무엇이었고, 어떻게 해결했나요?**
   - **대소문자 불일치 및 가짜 패딩 필터링 문제**: Have I Been Pwned의 range API 응답은 해시 뒤 35자리가 **대문자(UPPERCASE)**로 전달됩니다. 브라우저의 SHA-1 계산 결과가 소문자로 유지되면 일치하는 유출 비밀번호가 있더라도 "유출 내역 없음"으로 잘못 판정되는 치명적인 결함이 발생할 수 있었습니다.
   - 또한 `Add-Padding: true` 헤더를 사용하면 응답 크기 추측 공격을 방어하기 위해 유출 횟수가 `0`인 가짜 해시 항목들이 응답에 섞여 들어옵니다.
   - **해결**: 브라우저에서 계산된 해시를 즉시 `.toUpperCase()`로 변환하여 비교하도록 표준화하고, API 응답 라인 파싱 시 `count <= 0`인 가짜 패딩 항목을 필터링하여 정확한 유출 여부와 유출 횟수만을 신뢰성 있게 도출하도록 해결했습니다.

## 보안 점검 (사이버보안과 체크포인트)

1. **비밀번호 생성에 Math.random() 대신 crypto.getRandomValues()를 써야 하는 이유는 무엇인가요?**
   - `Math.random()`은 암호학적으로 안전하지 않은 **의사 난수 생성기(PRNG)**입니다. 내부 시드와 선형 합동/XorShift 알고리즘이 예측 가능하므로, 생성된 난수 몇 개만 수집해도 다음 난수나 이전 난수를 수학적으로 역추적할 수 있습니다.
   - 반면 **`crypto.getRandomValues()`**는 운영체제의 엔트로피 풀(하드웨어 노이즈, 인터럽트 타이밍 등)을 기반으로 동작하는 **암호학적으로 안전한 의사 난수 생성기(CSPRNG)**이므로 외부 공격자가 패턴을 예측할 수 없어 비밀번호 생성 및 암호화 키 생성에 반드시 사용해야 합니다.

2. **유출 확인 시 Network 탭에서 확인한 실제 요청 주소를 그대로 적어 주세요. 비밀번호나 전체 해시가 전송되지 않았나요?**
   - **실제 전송된 요청 주소**: `https://api.pwnedpasswords.com/range/5BAA6` (예: `password` 검사 시)
   - **검증 결과**: 개발자 도구 Network 탭 확인 결과, 원본 비밀번호(`password`)는 물론이고 SHA-1 전체 해시(`5BAA61E4C9B93F3F0682250B6CF8331B7EE68FD8`)도 일절 전송되지 않았습니다. 오직 **앞 5글자(`5BAA6`)만 전송**되었으며, 응답받은 해시 목록과 내 비밀번호의 뒤 35글자 대조 작업은 100% 브라우저 메모리 내에서 안전하게 수행되었습니다.

3. **k-익명성 방식으로도 서버가 알 수 있는 정보는 무엇인가요? (완전한 익명이 아닌 이유)**
   - k-익명성을 통해 비밀번호의 원본과 전체 해시는 안전하게 지켜지지만, 서버는 여전히 다음 정보들을 수집할 수 있으므로 완전한 무기명 상태는 아닙니다:
     1. 요청자의 **공인 IP 주소** 및 통신 패킷 메타데이터
     2. 요청이 발생한 **정확한 타임스탬프(요청 시각)**
     3. 요청에 포함된 해시의 **앞 5글자(Prefix)**
   - 따라서 서버 관리자나 네트워크 도청자는 사용자가 정확히 어떤 비밀번호를 확인했는지는 알 수 없으나, *"특정 IP의 사용자가 특정 시점에 특정 5글자로 시작하는 해시 그룹을 조회했다"*는 통계적 메타데이터는 인지할 수 있습니다.

## 나만의 확장 기능

1. **`Add-Padding: true` 프라이버시 패딩 적용**:
   - range API 호출 시 요청 헤더에 `'Add-Padding': 'true'`를 적용하여 패킷 크기 기반 사이드 채널 추측 공격을 방어하고, 유출 횟수가 `0`인 더미 패딩 데이터를 클라이언트에서 정밀하게 필터링했습니다.
2. **`AES-GCM 암호화 메모 금고` 탭 구현**:
   - `PBKDF2`(SHA-256, 100,000회 반복)로 마스터 비밀번호에서 AES-256 키를 파생하고, 매 암호화마다 랜덤 Salt(16B)와 IV(12B)를 생성하여 메모를 암호화·복호화할 수 있는 Zero-Knowledge 금고를 구축했습니다.
   - 비밀번호가 단 1글자라도 틀리면 AES-GCM 무결성 검증 실패 에러를 감지하여 *"비밀번호가 일치하지 않거나 데이터가 손상되었습니다. 복구할 수 없습니다."*라는 보안 경고를 표시합니다.
3. **화이트모드 ↔ 다크모드 원클릭 테마 전환**:
   - 사이버보안 대시보드 컨셉에 어울리는 고대비 다크 테마뿐만 아니라, 주간 업무 환경을 고려한 깔끔한 라이트(화이트) 테마를 CSS 변수 기반으로 완벽 지원합니다.
4. **암호 생성기 - 검사기 간 원클릭 연동 및 편의 옵션**:
   - CSPRNG 생성기에서 만든 강력한 비밀번호를 버튼 하나로 강도 검사창에 즉시 입력하여 유출 여부까지 원스톱으로 검증할 수 있도록 지원하며, 헷갈리기 쉬운 문자(`0, O, I, l, 1`) 제외 옵션을 제공합니다.
