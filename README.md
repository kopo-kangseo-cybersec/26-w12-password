# 🛡️ 클라이언트 중심 비밀번호 보안 점검 및 암호화 대시보드 (`26-w12-password`)

> 외부 UI 라이브러리(Tailwind, Bootstrap 등) 없이 **순수 CSS(모던 다크 테마)**와 브라우저 내장 **Web Crypto API**, 그리고 **k-익명성(k-Anonymity)** 모델을 결합하여 제작된 제로 지식(Zero-Knowledge) 지향 보안 도구입니다.

---

## 📌 1. 프로젝트 소개 및 앱의 정체성

본 애플리케이션은 단순한 회원가입 폼이나 비밀번호 생성 도구에 그치지 않고, 사용자가 입력한 비밀번호의 안전성을 스스로 진단하고, 암호학적으로 강력한 비밀번호를 생성하며, 클라이언트 측 종단간 암호화(End-to-End Encryption) 원리까지 직접 체험할 수 있도록 설계된 **「클라이언트 중심 비밀번호 보안 점검 및 암호화 대시보드」**입니다.

### 🛡️ 절대 준수 보안 가드레일 (Security Guardrails)
- **무출력 원칙 (Zero-Log)**: 입력되거나 생성된 평문 비밀번호, 마스터 키, 비밀 메모는 일절 `console.log`로 출력되지 않습니다.
- **휘발성 메모리 관리 (Zero-Storage)**: `localStorage`, `sessionStorage`, 쿠키 등 영구 브라우저 저장소를 일절 사용하지 않으며, 새로고침 시 모든 민감 데이터가 메모리에서 즉시 소멸합니다.
- **CSPRNG 전용 난수 생성**: 보안 취약성이 있는 `Math.random()` 대신 오직 암호학적으로 안전한 의사 난수 생성기인 `crypto.getRandomValues()`만을 사용합니다.
- **최소 전송 원칙 (k-Anonymity)**: 비밀번호 유출 확인 시 평문 비밀번호나 40자리 전체 SHA-1 해시를 전송하지 않고, 오직 앞 5글자(prefix)만 외부 API로 전송합니다.

## 🚀 2. 주요 기능 및 아키텍처

### 탭 1. 비밀번호 점검 및 생성 (2단 반응형 그리드)

#### 기능 A: 실시간 브라우저 내 비밀번호 강도 검사기
- **실시간 무통신 평가**: 서버 통신 없이 100% 브라우저 메모리 내에서 즉각 강도를 계산합니다.
- **4단계 보안 강도 게이지**: '매우 약함' (25%, 빨강) → '약함' (40~45%, 주황) → '보통' (70%, 파랑) → '강함' (100%, 초록)의 시각적 Progress Bar 및 배지를 제공합니다.
- **다차원 평가 기준**:
  1. **길이 기준**: 8자 미만(매우 약함), 8~11자(기본), 12~15자(우수), 16자 이상(최고점)
  2. **문자 조합 체크리스트**: 대문자(A-Z), 소문자(a-z), 숫자(0-9), 특수문자(!@#$%^&* 등)의 개별 충족 여부를 실시간 시각화
  3. **취약 패턴 감점**:
     - 사전 및 키보드 배열 패턴(`1234`, `qwer`, `asdf`, `password`, `admin`) 감지
     - 동일 문자 3회 이상 연속 반복(`aaa`, `111` 등) 감지
     - 위 패턴 발견 시 명확한 경고 문구를 표시하고, 비밀번호 길이가 길더라도 종합 강도를 **'약함' 이하로 강제 하향** 조정

#### 기능 B: k-익명성 기반 유출 확인 (Have I Been Pwned Range API)
- **사용자 제어 단발 요청**: 타이핑마다 요청을 보내지 않고, 사용자가 「유출 여부 확인」 버튼을 눌렀을 때만 1회 호출 (입력값 부재 시 비활성화).
- **Web Crypto SHA-1 해싱**: `crypto.subtle.digest('SHA-1', ...)`를 통해 계산된 해시를 반드시 대문자 40자리 16진수 문자열(`.toUpperCase()`)로 변환.
- **앞 5자리 전송 & `Add-Padding: true`**: `https://api.pwnedpasswords.com/range/${prefix}` 호출 시 패딩 헤더를 동봉하여 응답 크기 기반의 사이드 채널 추측 방지.
- **브라우저 대조 및 가짜 레코드 필터링**: 응답 목록에서 `Add-Padding`에 의해 포함된 유출 횟수가 `0`인 레코드를 대조 대상에서 제외한 뒤, 뒤 35자리(suffix) 일치 여부를 대조.
- **시각적 프로세스 다이어그램**: 실제로 네트워크로 나간 URL(`.../range/5BAA6`)과 브라우저 내부 비교 과정을 3단계 카드로 시각화.

#### 기능 C: 암호학적 안전 비밀번호 생성기 (CSPRNG)
- **길이 슬라이더**: 8자부터 32자까지 조절 가능 (기본값 16자).
- **문자 구성 강제**: 대문자, 소문자, 숫자, 특수문자 체크박스 제공 (최소 1개 이상 필수 선택 강제).
- **보장된 무작위성**: `crypto.getRandomValues()`를 사용해 선택된 문자 풀에서 최소 1글자씩 무조건 배정 후 Fisher-Yates 알고리즘으로 CSPRNG 셔플.
- **원클릭 클립보드 복사 & 점검기 즉시 적용**: 생성된 비밀번호를 복사하거나, 좌측 강도·유출 검사기에 즉시 전송하여 안전성을 바로 확인할 수 있는 UX 연동.

### 탭 2. 확장 기능: Zero-Knowledge AES-GCM 암호화 금고

- **PBKDF2 키 유도 (Key Derivation)**:
  - 무작위 Salt (16바이트, CSPRNG) 생성
  - 마스터 비밀번호에 `PBKDF2`(SHA-256, 100,000회 반복)를 적용하여 256비트 AES 암호화 키 파생
- **AES-GCM-256 인증 암호화 (Authenticated Encryption)**:
  - 12바이트 IV (CSPRNG) 생성
  - 평문 비밀 메모를 암호화하고 무결성 검증을 위한 인증 태그(Auth Tag) 생성
  - Salt, IV, 암호문을 Base64 문자열로 출력
- **복호화 및 무결성 검증**:
  - Salt, IV, 암호문, 마스터 비밀번호 입력 시 원문 복원
  - 비밀번호가 단 1글자라도 틀리거나 암호문이 변조되면 Web Crypto API의 `OperationError`를 포착하여 경고 메시지 표시:
    > *"비밀번호가 일치하지 않아 복호화할 수 없습니다. 키를 분실하면 누구도 복구할 수 없습니다."*
- **빠른 테스트 지원**: 암호화 결과를 복호화 입력창에 한 번에 채울 수 있는 [복호화 폼에 자동 입력] 기능 제공.

## 🔬 3. k-익명성(k-Anonymity)과 `Add-Padding` 동작 원리

### 1) k-익명성의 원리 (도서관 비유)
도서관 사서에게 *"제가 『1984』라는 책을 빌렸나요?"*라고 물어보면 사서는 내가 어떤 책을 찾는지 알게 됩니다.  
대신 *"제목이 '일'로 시작하는 책 대출 목록을 전부 주세요"*라고 요청하면, 사서는 목록 수백 권을 건네주고, 그 중에서 『1984』가 있는지 찾는 것은 **이용자 본인이 조용히 브라우저(로컬)에서 직접 확인**합니다.  
사서는 이용자가 그 수많은 책 중 어떤 책을 확인했는지 알 수 없습니다.

```
[1. 브라우저 내부]     "password" ──SHA-1──> 5BAA61E4C9B93F3F0682250B6CF8331B7EE68FD8
                                             ├── 5자 ──┤├──────── 35자리 ────────┤
                                              prefix                 suffix

[2. 외부 네트워크 전송]  GET https://api.pwnedpasswords.com/range/5BAA6
                       헤더: Add-Padding: true

[3. 서버의 반환 목록]   5BAA6으로 시작하는 수백 개의 [suffix:유출횟수]
                       ...
                       1E4C9B93F3F0682250B6CF8331B7EE68FD8:52256179
                       ...

[4. 브라우저 대조]     내 suffix가 목록에 존재하는가? → 일치! (52,256,179회 유출 판정)
```

### 2) `Add-Padding: true` 헤더의 역할
특정 5자리 prefix에 해당하는 유출 목록의 행(line) 개수와 패킷 크기(Byte)는 prefix마다 다릅니다.  
네트워크를 감청하는 도청자(ISP, 악의적 라우터, 프록시)는 요청된 URL의 앞 5글자와 **응답 패킷의 크기(Content-Length)**를 결합하여 사용자가 조회한 비밀번호의 범위를 좁히는 **트래픽 분석(Traffic Analysis) 사이드 채널 공격**을 시도할 수 있습니다.  
`Add-Padding: true` 헤더를 설정하면 서버가 응답 크기를 무작위화·평준화하기 위해 **유출 횟수가 `0`인 가짜 해시 레코드**를 응답에 섞어서 내려보냅니다. 클라이언트는 이를 파싱할 때 `count === 0`인 가짜 항목을 반드시 필터링해야 합니다.

## ⚠️ 5. k-익명성의 보안적 한계 고찰

k-익명성은 사용자의 원문 비밀번호와 40자리 전체 해시를 보호하지만, **완전한 무적의 익명성을 보장하는 것은 아닙니다.**

1. **메타데이터 노출**: HIBP 서버 및 중간 네트워크 경로는 사용자의 **공인 IP 주소, 요청 시각(타임스탬프), 접속 빈도**를 정확히 기록할 수 있습니다.
2. **해시 접두사(Prefix 5자리) 노출**: SHA-1의 16진수 5자리는 $16^5 = 1,048,576$개의 버킷 중 하나를 특정합니다. 즉, 전체 비밀번호 공간의 약 100만 분의 1로 범위가 좁혀지며, 특정 사용자가 비밀번호 점검 도구를 실행했다는 행위 자체가 노출됩니다.
3. **타이핑마다 조회할 경우의 치명성**: 만약 실시간 타이핑마다 API를 쏜다면 사용자가 글자를 칠 때마다 변화하는 해시 접두사 시퀀스가 서버에 기록되어 사실상 키로거처럼 동작할 수 있으므로, 반드시 **버튼 클릭 시에만 1회 전송**해야 합니다.

## 💡 6. 과제 핵심 힌트 5가지 모범 답안

### Q1. 앱의 정체성
> 단순 회원가입 폼이 아니라, 사용자가 비밀번호의 안전성을 스스로 진단하고 안전한 비밀번호를 발급받으며, 클라이언트 측 암호화 원리까지 체험할 수 있는 **「클라이언트 중심 비밀번호 보안 점검 및 암호화 대시보드」**로 설계했습니다.

### Q2. 강도의 기준
> 단순히 길이만 길다고 안전하지 않으므로 3가지 복합 기준으로 평가합니다.  
> 1. **길이**: 8자 미만(위험), 8~11자(최소 기준), 12~15자(권장), 16자 이상(안전)  
> 2. **문자 다양성**: 대문자, 소문자, 숫자, 특수문자 4가지 조합 수  
> 3. **패턴 감점**: `1234`, `qwer`, `password` 같은 사전적/키보드 배열 패턴이나 `aaa`, `111` 같은 연속 반복 문자가 포함되면 길이가 길어도 강도를 **'약함' 이하로 강제 제한**합니다.

### Q3. 대조 로직의 함정 (대소문자 불일치)
> Have I Been Pwned 서버가 응답으로 내려주는 SHA-1 해시 접미사(뒤 35자리)는 모두 **대문자(Uppercase)**입니다.  
> 반면 JavaScript에서 ArrayBuffer를 16진수 문자열로 변환(`toString(16)`)하면 기본적으로 **소문자(Lowercase)**가 생성됩니다. 이를 변환 없이 그대로 비교(`===`)하면 유출된 비밀번호도 일치하지 않는 것으로 판정되어 "안전"이라고 잘못 표시되므로, 반드시 `.toUpperCase()`로 대문자 통일 후 대조해야 합니다.

### Q4. 사용자 경험 (실시간 vs 버튼 클릭)
> **강도 검사**는 네트워크 통신 없이 브라우저 메모리에서만 연산하므로 실시간(타이핑마다) 피드백을 주는 것이 UX상 좋습니다.  
> 반면 **유출 확인**은 타이핑할 때마다 서버에 요청을 보내면 입력 도중의 중간 문자열(p, pa, pas...)에 대한 해시 접두사 5자리가 서버에 연달아 전송되어 정보 노출 범위가 넓어지고 불필요한 API 트래픽이 발생합니다. 따라서 보안성과 성능 모두를 위해 **「유출 여부 확인」 버튼을 눌렀을 때만 1회 요청하는 방식**이 올바릅니다.

### Q5. 확장 기능의 보안 원리
> 1. **`Add-Padding: true` 헤더**: 특정 해시 접두사(prefix)에 해당하는 유출 목록의 응답 패킷 크기(Byte)만 보고도 공격자나 중간 감청자가 어떤 비밀번호를 조회했는지 추측하는 트래픽 분석(Side-channel) 공격을 막기 위해, 서버가 응답 크기를 일정하게 맞추도록 유출 횟수가 0인 가짜 해시 항목을 섞어 보냅니다. 따라서 클라이언트에서는 파싱 시 유출 횟수가 0인 항목을 반드시 걸러내야 합니다.  
> 2. **AES-GCM 암호화 금고**: 비밀번호 원문을 저장하지 않고 PBKDF2(솔트 + 반복 해싱 100,000회)로 암호화 키를 즉석에서 유도해 AES-GCM으로 데이터를 잠급니다. 복호화 키를 서버나 DB에 보관하지 않기 때문에 비밀번호를 잊으면 수학적으로 복구가 불가능한 영지식(Zero-Knowledge) 암호화의 원리를 직접 확인할 수 있습니다.
